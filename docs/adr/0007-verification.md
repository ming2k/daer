# 0007. A test that cannot fail is a liability: every claim about the data path names its falsifier

- Status: Accepted
- Date: 2026-10-30
- Deciders: Ming Li
- Related: [ADR-0005](0005-kernel-policy-encoding.md), [ADR-0006](0006-wiring-ownership.md)

---

## Context and Problem Statement

`crates/daer-control/tests/transparent.rs` was the project's evidence that
"`daer run` now proxies traffic". Its own doc comment says an `nftables` rule
redirects a flow into `daer`'s transparent port, and it asserts that the reply
contains `hello`.

Both halves are wrong:

1. **No redirect rule exists anywhere in the repository.** `grep -rn "nft\|tproxy to"
   crates scripts` returns only prose in comments. The test never installs one, and
   nothing else does either.
2. **The assertion cannot fail.** The test starts its own origin on
   `127.0.0.2:18080` that answers `hello`, then asks whether the reply contains
   `hello`. I verified the vacuity directly by running the origin with **no daemon
   and no rules at all** and speaking the same bytes to it over a bare socket:

   ```text
   reply from origin alone: b"HTTP/1.1 200 OK\r\nContent-Length: 5\r\n\r\nhello"
   ```

The test was green, `docs/kernel-test-plan.md` cited it as the userland half of the
proof, and the data path it claimed to cover had never executed once.

This is not an isolated slip; it is a category. `scripts/kernel-check.sh` proves the
verifier accepts the object and that a `tc` program attaches to `lo` — both real,
both valuable — and then prints `Next: sudo daer run …` as if the next step were a
formality. It is not: it is the step that fails.

## Decision

### 1. Every end-to-end claim must name its falsifier

A test that asserts "the proxy worked" must include a **liveness check that the
proxy was involved**: a nonce only the daemon can produce, a counter that must
advance, or a deliberately induced failure that must appear. Concretely, the
transparent-proxy test now:

- installs the redirect itself (`nft tproxy`, from inside `unshare -Urn` or as root —
  a `skip`, not a pass, when neither is available);
- has the origin answer a **random nonce generated by the test**, so a hardcoded
  body cannot satisfy it;
- asserts `daemon.stats()` recorded the flow, so a client that reached the origin
  directly fails the test;
- is paired with a **negative control**: the same request to the same origin with
  the daemon stopped must *fail*. If the control passes, the fixture is broken and
  the test is reported as broken rather than as passing.

The negative control is the part that would have caught the original bug. It is now
part of the template for any test that claims to prove a data path.

### 2. Ignores are a debt with an owner

An `#[ignore = "needs CAP_NET_ADMIN"]` test is not coverage until it runs somewhere.
Each ignored test declares the environment it needs in its attribute, and
`scripts/kernel-check.sh` is extended to run them under `unshare -Urn` when the
privilege is available, so "no privilege here" is a `skip` with a reason instead of
a silent gap in CI. A test that is ignored, not run by any script, and cited in the
docs is the exact configuration that produced the vacuous test.

### 3. Documentation states what the current binary does

`README.md` claimed "verified end to end with `nftables tproxy` into a real origin".
It now claims what a check proves, and links to the check. Where a subsystem is
partial, the doc says which *tier* the daemon runs in (ADR-0005) and what that costs,
rather than listing the gap in a footnote while the headline says otherwise.

### 4. A green CI means the composition works

`cargo test --workspace` is necessary and insufficient. CI additionally:

- builds the object and asserts the ABI against it (already true);
- runs the kernel tests under `unshare` when available;
- runs `make pins` and `make schema-check` (already true);
- **fails when a configuration in `daer.example.toml` cannot route a flow through
  its own declared group**, which is the check that would have caught a default
  policy selecting no node.

## Consequences

- The test suite gets slower and more environment-dependent, and it starts failing
  for reasons that are real. That is the trade.
- Retracting a claim is part of the change: the previous "verified end to end"
  sentence is deleted rather than softened, because a softened claim is what let a
  vacuous test stand in for a missing data path for as long as it did.
- The negative-control pattern becomes the cheapest available defence against the
  next one: it costs one subprocess and it fails loudly when the fixture, not the
  product, is doing the work.

## What applying this ADR actually caught

Recorded because the pattern only earns its keep if the failures it finds are named. Two real
product defects were found by *trying to write the assertion*, not by reading the code:

1. **A current-thread runtime starves every spawned task.** The daemon spawns each relayed
   flow, each datagram forward and each reply pump, then waits in a `select!` where both
   alternatives are `Pending`. On a current-thread runtime a spawned task cannot run until the
   main future yields, so a datagram session was recorded as opened and its `send` never
   executed: the client timed out while the daemon reported a healthy session. `daer run` now
   uses a multi-threaded runtime, and `crates/daer-cli/tests/runtime.rs` asserts both halves of
   the property — that a current-thread runtime starves a spawned task *and* that a
   multi-threaded one does not — so the reason cannot rot into folklore.

2. **A `Mutex` held across an `await` stalls the whole relay.** `peer_for` opened a session
   while holding the table lock, and the receive loop takes the same lock. The lock now covers
   only the atomic part. This one has no test: the window is a dial, and every attempt to widen
   it deterministically either failed to reproduce or measured the fixture. It is a code shape
   rather than a behaviour, so it is documented in place instead of asserted, and saying so is
   more honest than a test that cannot fail.

Two further conclusions were reached and **withdrawn** during the same work, which is the other
half of this ADR:

- "UDP cannot be proven in one network namespace" was first attributed to `TPROXY` being a
  `PREROUTING` target. The real reason is topological: `tproxy` matches on the ingress
  interface, so the origin has to be in a second namespace. The test now says that, and the
  deployment guide says that, because a wrong reason in a comment is a wrong reason in the next
  engineer's head.
- A fixture whose origin accepted datagrams and never replied made three attempts to prove UDP
  fail. The product was fine; the fixture was mute. That is the negative-control lesson again,
  one layer down.
